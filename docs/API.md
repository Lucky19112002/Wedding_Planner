# API Contracts

**Status:** Phase 3 — database API (Supabase PostgREST + RPCs)  
**Depends on:** [SDD.md](SDD.md) Section 8, [DATABASE.md](DATABASE.md)  
**No React client is specified here.**

The application API is the **Supabase auto API** over tables/views plus **RPCs** in `schema/002_rls_policies.sql`. There is no custom HTTP gateway in this phase. Authorization is Row Level Security plus RPC checks. Errors follow SDD Section 8 (auth, forbidden, not found, validation).

---

## 1. Session

Every data and storage call uses a Supabase Auth session. Deactivated profiles fail helper `is_current_user_active()`. Lucky is the seeded Super Admin (`lucky@weddingplanner.app` until rotated).

---

## 2. Table resources (PostgREST)

Client reads/writes these names. RLS applies. Prefer archive RPCs instead of ad-hoc child updates when cascading.

| Resource | Typical operations |
| --- | --- |
| `profiles` | Select visible people; update own display name; Super Admin flags |
| `weddings` | Super Admin insert; select accessible weddings |
| `wedding_memberships` | Admin/Super Admin manage |
| `invitations` | Admin/Super Admin create via RPC; recipient select own pending |
| `events` | Admin/Super Admin write; members/viewers select non-archived |
| `participants` | Admin/Super Admin write |
| `outfits` | Admin/Super Admin; Member insert/update own |
| `outfit_images` | Same as parent outfit; max 5 active |
| `outfit_urls` | Same as parent outfit; max 5 active; `url` must be http(s) |
| `activity_logs` | Select per visibility; inserts from triggers/RPCs |

## 3. Progress views (read-only)

| View | Meaning |
| --- | --- |
| `v_outfit_progress` | Status weight 0–100; Dropped omitted |
| `v_participant_progress` | Average of active outfits, else 0 |
| `v_event_progress` | Average of participants; cancelled → null (excluded from wedding) |
| `v_wedding_progress` | `overall_completion_pct` = wedding overall completion |

Do not persist percentages in the client as source of truth.

---

## 4. RPCs

Call with `rpc('name', params)`. Tokens for invites are generated by the caller; the database stores **SHA-256 hex** only.

| Function | Purpose |
| --- | --- |
| `create_invitation(p_wedding_id, p_email, p_role, p_token)` | Pending invite, 14-day expiry |
| `accept_invitation(p_token)` | Membership + activity `invitation_accepted` |
| `reject_invitation(p_token)` | Pending → rejected |
| `resend_invitation(p_invitation_id, p_new_token)` | Pending/expired; new hash and expiry; old token invalid |
| `cancel_invitation(p_invitation_id)` | Pending/expired → cancelled |
| `archive_wedding(p_wedding_id, p_restore)` | Super Admin cascade |
| `archive_event(p_event_id, p_restore)` | Admin cascade |
| `archive_participant(p_participant_id, p_restore)` | Admin cascade |
| `archive_outfit(p_outfit_id, p_restore)` | Admin or owning Member cascade |
| `permanently_delete_wedding` / `_event` / `_participant` / `_outfit` | Super Admin; row must already be archived |

`p_restore := true` restores (clears `archived_at`). Default `false` archives.

---

## 5. Storage

- Bucket: `outfit-references` (private)
- Path: `{wedding_id}/{outfit_id}/{filename}`
- Upload only if the caller may write that outfit
- Database trigger still rejects a sixth **active** `outfit_images` row

---

## 6. Loading, errors, sync

Unchanged from SDD Section 8:

- Loading / saving / refreshing are client states
- Validation exceptions (caps, status, last Super Admin, expired invite) are not retried in a loop
- Backend remains authoritative; last complete field save wins until a later phase
- Offline writes are out of scope
